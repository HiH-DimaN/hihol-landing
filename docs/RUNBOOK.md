# RUNBOOK - hihol.ru

Операционная инструкция для инцидентов и деплоя. Пишется по фактам репозитория;
при расхождении с реальностью правится этот файл, а не память.

## 1. Что где живет

| Что | Значение |
|---|---|
| Домен | https://hihol.ru (плюс /ai) |
| Хост | 185.221.213.104 (Хостленд), панель Coolify на этом же сервере |
| Приложение в Coolify | `hihol-intake-compose`, compose-проект `qiskurnj5k7lmwuk9q379oyt` |
| Compose-файл | `deploy/intake.compose.yml` |
| Репозиторий | `github.com:HiH-DimaN/hihol-landing`, ветка `main` |

Сервисы в compose:

- **web** - Caddy отдает статический экспорт Next.js на внутреннем порту 3000.
  Проксирует `/api/*` на api. Health: `GET /healthz` -> 200.
- **api** - FastAPI (AI-анкета), внутренний порт 8000. Health: `GET /health`.
- **db** - PostgreSQL 16, том `intake-db`, наружу не публикуется.

TLS и публичные порты 80/443 держит Traefik (контейнер `coolify-proxy`).
Сеть `coolify` объявлена `external: true`, на web висит метка
`traefik.docker.network=coolify` - это фикс от 2026-07-20, не трогать без причины.

## 1a. Переменные окружения (задаются в Coolify UI, не в git)

| Переменная | Обязательна | Зачем |
|---|---|---|
| `POSTGRES_USER` | да | учетная запись базы заявок |
| `POSTGRES_PASSWORD` | да | пароль базы; генерировать `openssl rand -base64 24` |
| `POSTGRES_DB` | да | имя базы |
| `TELEGRAM_BOT_TOKEN` | нет | уведомления о новых заявках; без него они молча не приходят |
| `TELEGRAM_CHAT_ID` | нет | адресат уведомлений |
| `NEXT_PUBLIC_YM_ID` | нет | счетчик Яндекс.Метрики |

Ловушка, стоившая инцидента 2026-08-20: в `deploy/intake.compose.yml`
переменные объявлены через `${VAR:?сообщение}`. В чистом `docker compose` это
останавливает запуск при отсутствии переменной, но **Coolify этот синтаксис не
поддерживает** и подставляет текст сообщения как значение. В результате прод
несколько недель работал с логином и паролем базы, буквально равными
`set POSTGRES_USER` и `set POSTGRES_PASSWORD`, то есть с паролем, опубликованным
в репозитории.

Защита: `backend/app/config.py::assert_database_credentials` не дает API
стартовать на заглушечных или тривиальных паролях. Следствие для порядка
работ - **сначала задать переменные в Coolify, потом деплоить**; иначе
контейнер api осознанно не поднимется (сайт при этом продолжит работать,
перестанет отвечать только форма анкеты).

## 2. Нормальный деплой

1. Локально: `npm run build` - сборка должна быть зеленой.
2. `git push origin main` (в этом репозитории пуш идет с `--no-verify`, так как
   репозиторий не зарегистрирован в ITD-гейте; при сбое VPN повторить).
3. Coolify -> приложение -> **Deploy**. Автодеплоя нет, это ручной шаг.
4. Проверить публично: `curl -s -o /dev/null -w '%{http_code}' https://hihol.ru/healthz`
   должен вернуть 200, и на странице должен быть ожидаемый контент.

Деплой считается завершенным только после шага 4. Статус "Finished" в Coolify
означает, что контейнеры запущены, но не гарантирует, что сайт отвечает снаружи.

> Первый деплой после 2026-08-20 проводить в некритичное окно и посмотреть,
> как Coolify реагирует на добавленный compose-healthcheck сервиса web: раньше
> этого поля не было, статус контейнера брался только из образа. Ожидание -
> контейнер переходит в healthy за 5-35 секунд. Если Coolify начнет
> подсвечивать unhealthy или задерживать переключение, снять
> `docker inspect --format '{{json .State.Health}}' $(docker ps -qf 'name=web-')`
> и разбираться по фактам, а не откатывать вслепую.

## 3. Инцидент: сайт не открывается

Основной сценарий, случался дважды (см. раздел 6).

### 3.1. Диагностика за две минуты

```bash
curl -s -o /dev/null -w 'https: %{http_code}\n' https://hihol.ru/healthz
curl -s -o /dev/null -w 'http+Host: %{http_code}\n' -H 'Host: hihol.ru' http://185.221.213.104/
curl -s -o /dev/null -w 'bare80: %{http_code}\n' http://185.221.213.104/
```

Как читать:

- **Все три молчат (000)** - лежит сервер или прокси целиком. Идти в 3.2.
- **bare80 отвечает (404), Host-запрос молчит** - Traefik жив, но маршрут
  hihol.ru не находит бэкенд. Идти в 3.2.
- **Host-запрос отдает 301/302, https молчит** - маршрут поднялся, проблема в
  TLS: смотреть логи ACME (раздел 4).
- **https отдает 200, но страница не та** - это не инцидент доступности, а
  вопрос деплоя: проверить, какой коммит развернут.

Важно: проверять надо с второго канала (телефон по мобильной сети). Локальный
VPN и фильтрация по SNI дают ту же картину, что настоящее падение.

### 3.2. Лестница восстановления

Идти строго по порядку, после каждого шага ждать 60 секунд и повторять 3.1.

1. **Coolify -> Servers -> localhost -> Proxy -> Restart Proxy.**
   Лечит потерю маршрута/сети (оба прошлых инцидента вылечены этим).
2. **Coolify -> приложение -> Restart** (именно Restart, не Redeploy).
   Заставляет контейнеры переподключиться к сетям, Traefik увидит их заново.
3. **Rollback**: Coolify -> Deployments -> предыдущий успешный образ -> Deploy.
4. Перезагрузка сервера из панели Хостленда - крайняя мера.

### 3.3. Что НЕ делать

- Не менять сети и метки Traefik в `deploy/intake.compose.yml` "на всякий
  случай" во время инцидента: конфигурация рабочая, причина рецидива пока не
  доказана, вслепую можно сломать то, что чинится рестартом.
- Не удалять том `intake-db`.

## 4. Сбор доказательств (обязательно при рецидиве)

Причина повторяющегося отвала Traefik не доказана: рантайм-логи прокси ни разу
не снимали. При следующем инциденте снять их ДО рестарта - иначе цикл
"упало - рестартанули - забыли" повторится снова.

Через Coolify UI: Server -> Proxy -> **Logs** (рантайм-логи, не лог рестарта).

По SSH на 185.221.213.104:

```bash
# 1. Логи прокси: маршруты, сертификаты, ошибки
docker logs coolify-proxy --tail 300 2>&1 | grep -iE 'hihol|router|acme|error'

# 2. Видит ли Traefik контейнер web в общей сети
docker network inspect coolify --format '{{range .Containers}}{{.Name}} {{end}}'

# 3. Статус контейнеров приложения (health виден после фикса 2026-08-20)
docker ps --filter 'name=web-' --filter 'name=api-' --format '{{.Names}}\t{{.Status}}'

# 4. Отвечает ли сам контейнер, минуя прокси
docker exec $(docker ps -qf 'name=web-') wget -qO- http://127.0.0.1:3000/healthz && echo OK
```

Ответ на пункт 4 разделяет два мира: если контейнер отвечает, а снаружи нет -
проблема в прокси/сети; если не отвечает - проблема в приложении.

Собранный вывод сложить в `.itd-memory/` рядом с записью сессии.

## 5. Мониторинг

- **Внешний (основной)**: GitHub Actions `.github/workflows/uptime.yml`,
  проверка каждые ~30 минут с внешней площадки. Интервал выбран из биллинга:
  Actions округляет каждый запуск до минуты, при */30 это около 1440 минут в
  месяц и укладывается в бесплатный лимит приватного репозитория. Если
  репозиторий публичный, минуты не тарифицируются - можно ставить */10. При падении workflow падает,
  GitHub шлет письмо владельцу репозитория; при заданных секретах
  `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` дополнительно приходит сообщение в
  Telegram. Секреты задаются в GitHub: Settings -> Secrets and variables ->
  Actions -> New repository secret.
- **Внутренний (дополнительный)**: Coolify -> Notifications -> Telegram, плюс
  уведомления о статусе деплоя и unhealthy-контейнерах. Учитывать, что Coolify
  работает на том же сервере: при падении хоста этот канал молчит, поэтому он
  вторичен по отношению к внешнему.

Ручной запуск внешней проверки: вкладка Actions -> uptime -> Run workflow.
